# Account security reviews

## 2026-10-28 playlist and reconnection follow-up

The saved session was rejected by YouTube before any test mutation. Reconnection then exposed an Omarchy compatibility bug: xdg-settings returned `omarchy-browser.desktop`, which is a router rather than the underlying browser. The app now uses Omarchy's own `omarchy-cmd-default-browser` resolver for that entry. Both resolver processes use the existing cancellation and five-second deadline. Profile selection, the explicit cookie-read action, account preview and identity checks remain unchanged.

A fresh browser session matched the exact previously confirmed stable account identity, verified against YouTube and loaded liked music. That session was saved and restored byte-for-byte, then verified again. Switching between different Google or brand accounts remains unverified.

Live playlist checks reproduced two failures. A new playlist could initially return no contents, and an edit could initially return its previous metadata or occurrences after the service acknowledged the write. The account worker now retries only reads until the visible first-page state matches the acknowledged change. The limit is five reads with 500 ms between attempts. Each read checks the exact current session; network errors stop polling. Appended items and reorders outside the first page do not trigger a full-playlist scan. If the state remains unavailable, the error says the write was accepted and asks for a refresh. It never resubmits the mutation.

Deletion succeeded on the server but returned a command instead of `STATUS_SUCCEEDED`. The parser now also accepts `handlePlaylistDeletionCommand` when it names the exact requested playlist. Empty responses, another playlist's command and an explicit failure status remain rejected.

A disposable private playlist passed creation with its initial song, title and description changes, private visibility retention, adding a second song and a duplicate, distinct duplicate occurrence IDs, reordering one occurrence, removing only that occurrence, account-library discovery, editable-picker discovery and deletion. Fresh service reads checked the results after each operation. The deleted playlist was absent from the account library. Earlier diagnostic attempts were also deleted; no existing playlist was edited. Temporary account diagnostics and recovery records were removed, and credentials and action tokens were not logged or committed.

Validation passed all 146 ordinary tests, strict all-target Clippy, formatting, the metadata-only default-browser integration and the release build. The installed binary matches the verified release artifact. Native playlist controls, public/unlisted visibility changes, a different-account switch, ratings and other library mutations remain unverified. The automation driver captured the existing native Wayland window but refused targeted input because its Hyprland input plugin was unavailable; the installed update requires closing and reopening that running app.

The saved session also failed to decode after a desktop keyring round trip. JSON escape sequences had become literal control characters. Storage now uses prefixed base64 JSON and rejects values above secret-tool's 8192-byte stdin limit before changing the saved item. Valid legacy JSON remains readable. A synthetic keyring test now stores a full session with cookie-file tabs and newlines, then verifies exact bytes, decoding and repeatable cleanup. A separately authorized repair saved the current confirmed session, loaded identical bytes and verified its server identity. The installed app subsequently restored the account on restart without another browser read.

Category-filtered library search retained both Catalog and Library tabs, with Library selected at the second position. The positional assumption rejected this response. Search now prefers the service's stable scope identifier and rejects a missing or unselected requested scope. Positional compatibility applies only to responses without identifiers. A regression covers both tab orders and rejected scopes. Live signed-in checks passed all eight library categories of search and the uploads scope, including finding a known liked song in Songs results.

Validation passed all 142 ordinary tests, strict all-target Clippy, formatting and a release build. Focused integrations passed the synthetic Secret Service round trip, all public search filters/suggestions and public history-destination validation. Separate authorized live checks loaded all twelve account library categories, verified saved-session restoration and sent one history report for a song the user had already played. The report returned HTTP 204; a later read confirmed that song first in server history. The installed release then restored the saved account, played the existing selected song muted for 31 seconds and paused. A separate server read confirmed that native play as the newest history entry. The Home screen showed no history error. Opening the History screen could not be verified because background input had no effect and the compositor refused foreground focus. Temporary diagnostics were removed and no credentials or tracking values were logged or committed.

Account switching, brand-account behavior, ratings, playlist edits, history removal and cross-client library changes remain unverified. These fixes and checks do not establish complete parity or absence of vulnerabilities.

## 2026-10-27 signed-in Zen reader repair

A real signed-in Zen session reproduced an exclusive SQLite lock that prevented the reader from reaching YouTube. The reader now uses a bounded, twice-checked database/WAL/journal snapshot only after a busy or locked result. The private copy stays in the RAM-backed runtime directory, uses owner-only permissions, and is removed by Rust after the helper exits or is killed on cancellation. Only filtered YouTube rows leave the helper. SQLite connections close explicitly. Modern Firefox schema expiry timestamps are filtered in milliseconds and converted to seconds for playback.

Once the reader succeeded, live verification exposed a second blocker. YouTube returns a 302 from the account-indexed root to its canonical root. Verification now retries only that exact root with the same account headers, then requires the original full identity. Automatic redirects and other destinations remain disabled.

Validation passed 138 ordinary Rust tests, including five synthetic Python reader tests, formatting, strict all-target Clippy and the release build. The new fixture keeps an exclusive-lock writer running with the latest login only in WAL, verifies modern expiry filtering, and checks that the original files remain unchanged. A separate read-only check of the user's existing signed-in session passed bootstrap, account-menu identity verification, and authenticated playlist-page loading. The diagnostic check saved no session, sent no library mutations or playback-history reports, and logged no cookie values. The installed release subsequently reached the connected state in the native app and rendered the personalized Home and playlists. Authenticated playback, saved-session restoration, account switching and cross-client writes still require verification.

## 2026-10-27

A bounded readiness review found that ordinary quit could still detach persistence or edits after the connection indicator cleared. Shutdown now drains the existing account worker for every exit. A synthetic persistence test verifies that finishing waits for an accepted save without clearing the current session.

Connection no longer captures the first signed-in channel automatically. The user selects a Google or brand account in the dedicated browser, then confirms it in native Settings. Failed capture or verification leaves that browser open for an explicit retry. Cancel connection preserves the previous connection and its saved keyring item. Existing stable-identity checks remain enforced. Confirmation and cancellation tests use synthetic operations, without a Google account.

The source review covered every changed source file between e9cfcdf and 5899fb5. It found no reportable vulnerability in that gated build. This is a bounded review, not a guarantee that the application has no vulnerabilities.

Subsequent hardening binds queued edits, persistence, catalog and song-detail jobs to a verified session. Failed verification preserves the previous session. Connection completion must match the active, uncancelled operation in both the worker and UI. Persistence starts only after UI acceptance and playback credential allocation; revoked writes are removed.
