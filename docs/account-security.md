# Account security

Account connection opens the default browser and supports native Zen and Firefox profiles. Authenticated playback and cross-client sync still require real-account verification.

The app resolves the browser's configured default profile from profile metadata. Install-specific defaults take precedence over legacy profile defaults. Ambiguous configurations fail instead of guessing from file timestamps. Opening the browser reads no cookies. Settings names the source browser and profile; only **Read YouTube session** authorizes reading its cookies. A small embedded Python helper opens `cookies.sqlite` through SQLite's read-only URI mode, including committed WAL changes. Its query selects only exact YouTube root, Music and www hosts, the root path, unexpired cookies, and the normal unpartitioned cookie store. It does not copy the database or read saved passwords or other sites. Private windows and containers are unsupported. Cookie values travel through private anonymous RAM output files, never command arguments or persistent exports.

The snapshot is sent only to YouTube Music, with sensitive request headers and redirects disabled. Host-only cookies are not sent to sibling hosts. The bounded page bootstrap must contain a signed-in state, explicit Google account index, full `DATASYNC_ID` and client version. The delegated identity is derived from that server response, with conflicting account fields rejected. Page scripts are never executed. A second account-menu check provides the account name and handle and verifies the same stable identity, falling back to a fresh matching page when the menu omits identity. Missing, mismatched or logged-out identity fails closed.

The preview remains unconnected until the user chooses **Connect as [account name]**. The browser's active tab is not inspected, so the returned identity may be the default account instead of the tab's selected Google or brand account. Switching the browser account and retrying is possible but not guaranteed to select a different identity. The app never silently treats a cookie jar as proof of the user's intended account. Arbitrary cookie-file imports remain unsupported. This is browser-session access, not a scoped OAuth grant.

A new connection becomes active only after this confirmation, the player's acknowledgement of credential installation, and acceptance of the same uncancelled operation. It can then be queued for keyring storage. Failed verification, rejected previews, cancellation and failed playback activation preserve the previous shared session and saved keyring item. Stale events cannot activate or save credentials. The normal browser is user-owned and remains open on success, cancellation or app exit. Normal quit cancels pending connection work and joins the account worker, including accepted persistence and mutations. Forced termination cannot provide that guarantee. A private, no-follow process lock prevents concurrent app instances from racing shared credentials and library writes.

Storage checks the exact session before and after writing and removes a write revoked during storage. Credentials are saved through the desktop Secret Service keyring using libsecret's `secret-tool`. Keyring failure has no plaintext-file fallback. Cookie rotation or expiry can require an explicit reconnection.

Each queued edit is bound to the exact verified session that created it. The session is checked before resolving the request and again before sending the mutation, so signing out during an artist or album lookup prevents the later write. An already dispatched request can finish during sign-out. An account switch or sign-out invalidates stale edits. Connection completion must match the active, uncancelled operation before either shared credentials or the UI can activate it. Catalog and playback-detail jobs use fixed session snapshots. An account change invalidates displayed results, navigation history, overlays, pending song details and in-memory account action tokens. Authenticated API requests do not follow redirects. Signing out clears active account authority and navigation history, requests playback credential cleanup and removes the keyring entry. Success requires both the player acknowledgement and keyring removal. A failure leaves a Retry sign-out control and blocks reconnecting until cleanup succeeds. Closing the window during sign-out waits for the serial account worker. Keyring lookup, store and removal each have a 30-second limit and owned child-process cleanup. Lookup is cancellable and captures output in private anonymous RAM files, avoiding full-pipe stalls. Quitting or cancelling restoration does not clear a saved connection. Shutdown can still wait for earlier in-flight account requests.

Playback history uses a separate session-bound command after mpv starts the selected track. Before submitting history, the player response must confirm the full selected primary or brand account identity and the requested video. Conflicting account hints and logout are rejected. The destination must use HTTPS on port 443 at `s.youtube.com` or `www.youtube.com`, with the exact `/api/stats/playback` path and one matching video ID. User information, fragments, ambiguous authorities and redirects are refused. The session is checked before the player call and again before the history request. Authentication is generated fresh for each request. Only HTTP 204 acknowledges a report. Tracking URLs stay in memory and are stripped from transport errors. An already dispatched request can finish during sign-out. Connected plays do not populate guest history.

The account exports sealed, owner-readable anonymous RAM files for cookies and selected account identity. Playback makes a separate owner-readable, writable anonymous RAM cookie copy because yt-dlp rewrites its cookie jar after extraction. An ordered extractor configuration also stays in sealed RAM. None of these has a disk pathname. Credential replacement stops mpv, consumes a marker in its event queue, waits for any started file to end, and installs the new options before closing the old files. The marker prevents a delayed start event from bypassing that wait. On the tested mpv 0.41.0 build, a stop reply alone precedes extractor termination; the file-end event follows it. Synthetic local extractors verify termination and descriptor revocation through replacement, clearing, fatal exit and player shutdown. HTTP cookie and authorization headers are marked sensitive so request debug formatting redacts them. Raw extractor warnings are not forwarded to the UI. The app disables core dumps; this relies on the host crash handler respecting the limit, as the development machine's systemd-coredump does. Credentials are never passed on command lines, written to application logs, or committed to Git.

Authenticated playback uses an embedded extractor bound to the selected Google account index and full primary/brand account identity. It requires matching account identity from the server before returning playable formats. Explicit logout, mismatched or missing identity, redirects, a missing plugin, or an unsupported yt-dlp version fail closed. Only the reviewed HTTP handler is available to that extractor, and it rejects redirects before contacting a second destination. User yt-dlp configuration and external plugins are disabled. The supported authenticated extractor version is exactly 2026.08.19; a different version requires another compatibility review. Public guest playback uses the stock extractor without account credentials.

These controls do not establish immunity from vulnerabilities. A compromised user session or privileged process can still access credentials in memory or through an unlocked keyring. Google browser sessions grant broader YouTube access than a narrowly scoped OAuth grant. The internal API is unofficial and account operations require real-service verification. The app must report rejected writes rather than silently saving a local substitute.

Native video uses one in-process libmpv core. Decoder and graphics-driver faults can therefore crash or stall the whole app; the former separately managed player process provided a stronger fault boundary. Joining renderer and player workers has no hard timeout if a driver blocks. This is not a credential sandbox. The renderer owns its child windows and graphics resources, detaches before dialogs or window destruction, and stops before the player core and credential files are released. Xlib threading is initialized before GPUI or libmpv starts. Hardware decoding uses mpv's auto-safe mode. Existing extractor identity checks, private RAM credentials and acknowledged credential replacement remain required for audio and video alike.

Automated checks use synthetic profiles and cookies to verify install-default selection, ambiguous-profile rejection, read-only WAL access, exact cookie hosts and store isolation, cookie-header injection rejection, explicit server identity, fresh authorization, redacted diagnostics, and anonymous credential permissions and lifetimes. They also cover session-bound edits, history reports, revoked storage and cleanup after the UI receiver closes. Offline extractor tests exercise primary and brand identities, conflicting responses, logout, redirect refusal, sealed inputs, version checks and plugin failure. Live mpv checks verify guest playback through null audio output. Real Google credentials are not used by these tests. Authenticated playback and cross-client account verification remain separate requirements.

Normal quit during pending sign-in was reproduced before the fix and passed afterward with both processes gone and the temporary profile removed. The Secret Service check uses a unique synthetic item and verifies storage, lookup, removal and repeated removal. An already absent item counts as successful cleanup; backend errors still fail sign-out.
