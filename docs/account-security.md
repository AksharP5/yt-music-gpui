# Account security

Account connection, saved-session loading and cookie import are disabled while the authentication changes are reviewed and verified. Do not use an older prototype sign-in build.

The intended connection flow opens Google's real sign-in page in a dedicated Chromium process. It launches the browser binary directly, disables extensions and sync, and uses a private inherited pipe. There is no TCP debugging listener. The temporary browser profile must be inside the current user's private RAM-backed desktop runtime directory. The browser is terminated and reaped on success, cancellation, timeout, or failure; its temporary profile is owned by that process guard.

Only YouTube-domain cookies are exported from that temporary profile. The API verifies the account with YouTube Music before storing or activating credentials. Failed verification preserves the previous verified session. Credentials are saved through the desktop Secret Service keyring using libsecret's `secret-tool`. Keyring failure has no plaintext-file fallback. Existing browser profiles and saved passwords are not inspected.

Each queued edit is bound to the exact verified session that created it. An account switch or sign-out invalidates stale edits. Catalog jobs use a fixed session snapshot, and an account change invalidates the previous displayed results and navigation history. Authenticated API requests do not follow redirects. Signing out stops playback, closes the playback credential file, clears active account authority, and requests removal of the keyring entry. A keyring removal failure is reported.

The account exports a sealed, owner-readable anonymous RAM file. Playback makes a separate owner-readable, writable anonymous RAM copy because yt-dlp rewrites its cookie jar after extraction. Neither file has a disk pathname. Credential replacement waits for mpv to acknowledge stopping the previous extraction and installing the new options before closing the old RAM file. HTTP cookie and authorization headers are marked sensitive so request debug formatting redacts them. Raw extractor warnings are not forwarded to the UI. The app disables core dumps; this relies on the host crash handler respecting the limit, as the development machine's systemd-coredump does. Credentials are never passed on command lines, written to application logs, or committed to Git.

These controls do not establish immunity from vulnerabilities. A compromised user session or privileged process can still access credentials in memory or through an unlocked keyring. Google browser sessions grant broader YouTube access than a narrowly scoped OAuth grant. The internal API is unofficial and account operations require real-service verification. The app must report rejected writes rather than silently saving a local substitute.

Automated checks cover exact cookie names and domain filtering, fresh authorization, redacted request diagnostics, anonymous credential files and their permissions/lifetimes, fragmented private-pipe messages, session-bound edits, and the disabled import boundary. A live Chromium test verifies the private transport with extensions disabled and no debugging port. A live mpv test verifies public playback with invented initial cookies, replacement cookies and cleared credentials. A source review of the nine changed source files at revision 5899fb5 found no reportable vulnerability in that gated build. This result does not certify later changes or establish zero vulnerabilities. Cross-client account verification remains a separate release requirement.
