# Account security

Account connection and saved-session loading are available for controlled live verification after the boundary checks passed. Authenticated compatibility and cross-client sync remain unverified. Cookie imports are unsupported. Do not use an older prototype sign-in build.

The connection flow opens Google's real sign-in page in a dedicated Chromium process. It launches the browser binary directly, disables extensions and sync, and uses a private inherited pipe. There is no TCP debugging listener. The temporary browser profile must be inside the current user's private RAM-backed desktop runtime directory. The browser is terminated and reaped on success, cancellation, timeout, or failure; its temporary profile is owned by that process guard. A private, no-follow process lock prevents concurrent app instances from racing shared credentials and library writes; the lock is released automatically on exit.

Only YouTube-domain cookies are exported from that temporary profile. The API verifies the account with YouTube Music before activating credentials. Failed verification preserves the previous verified session. A new connection is queued for storage only after the UI accepts its active operation and allocates its playback credentials. Cancelled or abandoned connection events cannot save credentials. Storage checks the exact session before and after writing, and removes a write revoked during storage. Credentials are saved through the desktop Secret Service keyring using libsecret's `secret-tool`. Keyring failure has no plaintext-file fallback. Existing browser profiles and saved passwords are not inspected. Cookie imports are rejected because a cookie jar does not identify the selected Google or brand account.

Each queued edit is bound to the exact verified session that created it. An account switch or sign-out invalidates stale edits. Connection completion must match the active, uncancelled operation before either shared credentials or the UI can activate it. Catalog and playback-detail jobs use fixed session snapshots. An account change invalidates displayed results, navigation history, overlays, pending song details and in-memory account action tokens. Authenticated API requests do not follow redirects. Signing out stops playback, closes the playback credential files, clears active account authority and navigation history, and requests removal of the keyring entry. Closing the window during sign-out waits for the serial account worker to finish that cleanup. Keyring store and removal each have a 30-second limit and owned child-process cleanup. A removal failure is reported; sign-out must not be described as complete before removal succeeds.

Playback history uses a separate session-bound command after mpv starts the selected track. Before submitting history, the player response must confirm the full selected primary or brand account identity and the requested video. Conflicting account hints and logout are rejected. The destination must use HTTPS on port 443 at `s.youtube.com` or `www.youtube.com`, with the exact `/api/stats/playback` path and one matching video ID. User information, fragments, ambiguous authorities and redirects are refused. The session is checked before the player call and again before the history request. Authentication is generated fresh for each request. Only HTTP 204 acknowledges a report. Tracking URLs stay in memory and are stripped from transport errors. An already dispatched request can finish during sign-out. Connected plays do not populate guest history.

The account exports sealed, owner-readable anonymous RAM files for cookies and selected account identity. Playback makes a separate owner-readable, writable anonymous RAM cookie copy because yt-dlp rewrites its cookie jar after extraction. An ordered extractor configuration also stays in sealed RAM. None of these has a disk pathname. Credential replacement waits for mpv to acknowledge stopping the previous extraction and installing the new options before closing the old files. HTTP cookie and authorization headers are marked sensitive so request debug formatting redacts them. Raw extractor warnings are not forwarded to the UI. The app disables core dumps; this relies on the host crash handler respecting the limit, as the development machine's systemd-coredump does. Credentials are never passed on command lines, written to application logs, or committed to Git.

Authenticated playback uses an embedded extractor bound to the selected Google account index and full primary/brand account identity. It requires matching account identity from the server before returning playable formats. Explicit logout, mismatched or missing identity, redirects, a missing plugin, or an unsupported yt-dlp version fail closed. Only the reviewed HTTP handler is available to that extractor, and it rejects redirects before contacting a second destination. User yt-dlp configuration and external plugins are disabled. The supported authenticated extractor version is exactly 2026.08.19; a different version requires another compatibility review. Public guest playback uses the stock extractor without account credentials.

These controls do not establish immunity from vulnerabilities. A compromised user session or privileged process can still access credentials in memory or through an unlocked keyring. Google browser sessions grant broader YouTube access than a narrowly scoped OAuth grant. The internal API is unofficial and account operations require real-service verification. The app must report rejected writes rather than silently saving a local substitute.

Native video uses one in-process libmpv core. Decoder and graphics-driver faults can therefore crash or stall the whole app; the former separately managed player process provided a stronger fault boundary. Joining renderer and player workers has no hard timeout if a driver blocks. This is not a credential sandbox. The renderer owns its child windows and graphics resources, detaches before dialogs or window destruction, and stops before the player core and credential files are released. Xlib threading is initialized before GPUI or libmpv starts. Hardware decoding uses mpv's auto-safe mode. Existing extractor identity checks, private RAM credentials and acknowledged credential replacement remain required for audio and video alike.

Automated checks cover exact cookie names and domain filtering, fresh authorization, redacted request diagnostics, anonymous credential files and their permissions/lifetimes, fragmented private-pipe messages, session-bound edits and history reports, revoked storage, cleanup after the UI receiver closes, and the disabled import boundary. History tests reject missing or mismatched server identity, stale sessions, unsafe destinations and unconfirmed status codes. Offline extractor tests exercise multiple account indexes, primary and brand identities, conflicting configs and player responses, logout, missing server proof, redirect refusal, sealed inputs, version checks and plugin failure. A live Chromium test verifies the private transport with extensions disabled and no debugging port. Live mpv checks verify public guest playback, pause, seek and speed changes. A guest player inspection validates the history destination without submitting a report. Real Google credentials are never used by these tests. A source review of the nine changed source files at revision 5899fb5 found no reportable vulnerability in that gated build. This result does not certify later changes or establish zero vulnerabilities. Authenticated playback and cross-client account verification remain separate release requirements.
